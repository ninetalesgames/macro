# Macro Journal Project Overview

## What This Project Is

Macro Journal is a single-page nutrition and weight tracking app built with React,
TypeScript, and Vite. It lets a user:

- Log daily calories, protein, weight, and notes.
- Enter calories, protein, and weight together in one daily entry card.
- Browse and edit entries using a monthly calendar.
- View seven-day averages for calories, protein, and weight.
- Compare the current seven-day weight average with the previous seven days.
- See calendar entries color-coded as cutting, maintenance, or bulking zones.

The app uses Firebase Authentication and Cloud Firestore to sync journal
entries between devices. A per-account `localStorage` cache keeps startup fast
and preserves data while the app is temporarily offline.

### Main Folders

#### `src/`

Contains the application source code.

- `main.tsx` is the React entry point. It finds the `#root` element in
  `index.html` and renders the `App` component inside React `StrictMode`.
- `App.tsx` contains the journal's data types, state, calculation helpers,
  event handlers, and all UI components.
- `firebase.ts` initializes Firebase Authentication and Cloud Firestore.
- `App.css` contains the journal-specific layout and component styles.
- `index.css` contains global styles, root sizing, typography, color variables,
  and some starter theme styles.
- `assets/` contains image assets. The current `App` component does not import
  these files.

#### `public/`

Contains static files copied directly into the production build. `icon.png` is
used as the page favicon from `index.html`. The SVG files are currently not
referenced by the app.

#### `dist/`

Contains the generated production build created by `npm run build`. This folder
is deployed to GitHub Pages and should not be edited by hand.

#### `node_modules/`

Contains installed npm dependencies. It is generated by `npm install` and
should not be edited or committed.

## How the App Starts

The application startup flow is:

1. `index.html` provides the page shell and a `<div id="root"></div>`.
2. `index.html` loads `/src/main.tsx`.
3. `main.tsx` imports the global styles and renders `App`.
4. `App.tsx` imports `App.css`, loads saved journal entries, and renders the
   complete journal interface.

Because the app is currently small, nearly all application behavior lives in
`App.tsx` instead of being split into separate component or utility files.

## Journal Data Setup

Each journal day uses this shape:

```ts
type DayEntry = {
  calories?: number;
  protein?: number;
  weight?: number;
  notes?: string;
};
```

Entries are stored in an object keyed by a local date string:

```ts
type EntriesMap = Record<string, DayEntry>;
```

An example saved entry looks like:

```json
{
  "2026-06-09": {
    "calories": 2100,
    "protein": 160,
    "weight": 83.4,
    "notes": "Tennis day"
  }
}
```

The date keys use the `YYYY-MM-DD` format and are generated using the user's
local date rather than UTC.

## State and Persistence

The `App` component manages these main pieces of state:

- `entries`: all saved journal entries.
- `calendarMode`: whether calendar cells display calories, protein, or weight.
- `selectedDay`: the date currently being edited.
- `viewMonth`: the month currently shown in the calendar.
- `saveStatus`: shows whether the latest local changes have been saved.
- `user` and `authReady`: track Google sign-in state.

Before sign-in, legacy entries are loaded from this browser storage key:

```text
macro-journal-v2-entries
```

After Google sign-in, entries are stored in Firestore at:

```text
users/{firebaseUserId}/entries/{YYYY-MM-DD}
```

Existing local entries are uploaded when a user first signs in. If both local
and cloud data exist for the same date, the cloud entry wins. After migration,
the browser cache is separated by Firebase user ID and Firestore changes are
received in real time.

Firestore access is protected by the security rules in `rules.txt`, which allow
signed-in users to read and write only their own dated entries.

## Main Interface Sections

### Daily Entry Card

The first panel is a complete entry form for the selected date. It defaults to
today and lets the user enter calories, protein, and weight together. Notes are
available in a collapsible section to keep everyday logging compact.

Changes save immediately, and the header shows whether data is saved locally,
syncing, synced, or experiencing a sync issue. When a historical date is
selected from the calendar, the same card edits that date and displays a
**Back to today** action.

### Weekly Stats

A compact stats strip below the entry card shows:

- Seven-day average weight.
- Seven-day average calories.
- Seven-day average protein.
- Weight trend compared with the previous seven-day period.

Only days with a logged value are included in an average.

### Calendar

The calendar is Monday-first and displays one month at a time. Users can move
between months, return to today, and click any date to select it.

The mode buttons change what each date displays:

- `Calories`: compares logged calories with the calorie target.
- `Protein`: compares logged protein with the protein target.
- `Weight`: compares weight with the most recent logged weight from the
  preceding 30 days.

The **Clear entry** button removes all values and notes from the selected date.
Calories and protein are rounded to non-negative whole numbers. Weight is
rounded to one decimal place.

## Targets, Trends, and Colors

The current fixed targets are defined near the top of `App.tsx`:

```ts
const DEFAULT_CALORIE_TARGET = 2100;
const DEFAULT_PROTEIN_TARGET = 160;
```

Calendar colors are assigned as follows:

- Green (`tone-cut`): cutting range, protein target reached, or weight trending
  down.
- Yellow (`tone-maintain`): maintenance range or stable weight.
- Red (`tone-bulk`): bulking range, low protein, or weight trending up.
- Gray (`tone-empty`): no value has been logged.

For calories, values within 150 calories of the target are maintenance. For
weight trends, the app compares the selected day's seven-day average against
the seven days before it. A difference smaller than `0.15 kg` is considered
stable.

## Styling Setup

`App.css` provides the active visual design:

- Refined dark page background with lightweight panels.
- Mobile-first daily entry fields and compact weekly stats.
- Responsive entry and calendar grids.
- Form, navigation, and button styling.
- Green, yellow, red, and gray tone classes.
- Mobile layout changes below `820px`.

`index.css` contains only the global page-height defaults. The active theme and
component styling live in `App.css`.

## Configuration

### `package.json`

Defines the project dependencies and npm scripts:

```text
npm run dev       Start the Vite development server
npm run build     Type-check and create the production build
npm run lint      Run ESLint
npm run preview   Preview the production build locally
npm run deploy    Build and publish dist/ to GitHub Pages
```

The main runtime dependencies are React, React DOM, and Firebase. Vite,
TypeScript, ESLint, and `gh-pages` are development dependencies.

### `vite.config.ts`

Enables the React plugin and sets the production base path to `/macro/`. This
matches the GitHub Pages deployment configured in `package.json`:

```text
https://ninetalesgames.github.io/macro/
```

### TypeScript and ESLint

- `tsconfig.json` connects the app and Vite configuration TypeScript projects.
- `tsconfig.app.json` applies strict TypeScript settings to `src/`.
- `tsconfig.node.json` applies TypeScript settings to `vite.config.ts`.
- `eslint.config.js` enables recommended JavaScript, TypeScript, React Hooks,
  and React Refresh lint rules.

## Where to Make Common Changes

- Change journal behavior, calculations, data fields, or UI sections in
  `src/App.tsx`.
- Change the journal's appearance or responsive layout in `src/App.css`.
- Change global typography or page-wide defaults in `src/index.css`.
- Change the browser title or favicon in `index.html`.
- Change the GitHub Pages path in `vite.config.ts` and the deployment URL in
  `package.json`.
- Add static public files to `public/`.

As the project grows, `App.tsx` is the main candidate to split into separate
folders such as `components/`, `utils/`, and `types/`.
